# Адаптивная загрузка экранов через Addressables

## Подключение

Текущая реализация рассчитана на Unity 6.0+, uGUI 2.0 и Addressables 2.7.6.
Зависимости объявлены в `package.json`; интеграция выделена в сборку
`SimpleUIScreensSystem.Addressables`, политика популярности — в основном runtime.
UI Toolkit не используется.

1. Вручную сверстайте экран через uGUI и сохраните его как prefab.
2. Добавьте `UIScreen` на корень prefab. Теперь этот компонент можно использовать
   непосредственно; для собственной логики можно наследоваться от него.
3. Назначьте кнопки закрытия, модальный контейнер и настройку анимации.
4. Отметьте prefab как Addressable. Сам prefab и его тяжёлые ресурсы не должны
   одновременно удерживаться прямыми ссылками из стартовой сцены.
5. Создайте `Create → Simple UI → Addressable Screen Catalog`.
6. Для каждого экрана задайте уникальный **Code Name**, например `Settings` или
   `Inventory`, ссылку на prefab, приоритет 0–10, оценку резидентной памяти в MB и
   разрешение предзагрузки. Стабильный ID создаётся автоматически и не зависит от
   Code Name. Один prefab должен соответствовать одной записи каталога.
7. В инспекторе каталога нажмите **Generate Screen Keys...**, сохраните файл,
   например, в `Assets/Game/UI/Generated/Screens.cs`. По умолчанию namespace —
   `Game.UI`, имя класса — `Screens`; оба можно настроить в каталоге.
   Сгенерированный файл принадлежит проекту пользователя и должен храниться в его
   системе контроля версий вместе с каталогом. Размещать его внутри пакета нельзя.
8. Добавьте `AddressableUIRoot` на активный объект, назначьте каталог и контейнер
   экранов под Canvas. Не выключайте этот объект для обычного скрытия окна:
   отключение корня освобождает все его экземпляры и кеш.
9. Подготовьте Addressables content build для проверки в player. Editor Play Mode
   с Asset Database проверяет логику, но не реальную стоимость загрузки bundles.

Root имеет собственную регистрацию по `ScreenId` и не добавляет загружаемые экраны
в сценовый `UINavigator`. В примере `_navigator` имеет тип `AddressableUIRoot`.
`UINavigator` обслуживает экраны, размещённые в сцене: их ключ задаётся в поле **ID**
компонента `UIScreen`, а константы `ScreenId` для них объявляются в проекте вручную.
Оба навигатора принимают один и тот же тип ключа. Добавление новых экранов не
требует изменения пакета.

```csharp
using SimpleUIScreensSystem.AddressableUI;
using Game.UI; // Namespace сгенерированного класса Screens.
using UnityEngine;

public sealed class MenuActions : MonoBehaviour
{
    [SerializeField] private AddressableUIRoot _navigator;

    public void SelectInventoryTab()
    {
        _navigator.ReportAction("inventory.tab_selected");
        _navigator.Open(Screens.Inventory);
    }

    public void CloseInventory() => _navigator.Close(Screens.Inventory);
}
```

## Типизированные ключи

```csharp
_navigator.Open(Screens.Settings);
_navigator.Close(Screens.Settings);
_navigator.TryGetScreen(Screens.Settings, out var screen);
```

`ScreenId` — неизменяемая структура с ordinal-сравнением и хешированием без
упаковки при использовании `Dictionary<ScreenId, ...>`. Ключи чувствительны к
регистру; `default(ScreenId)` невалиден. `Open` и `Close` отклоняют невалидные и
неизвестные ключи, `TryGetScreen` возвращает `false`.

Идентичность разделена на три независимые части:

| Часть | Назначение |
|---|---|
| Стабильный ID | Связывает каталог, обращения и статистику; сохраняется при переименовании |
| Code Name | Имя поля в сгенерированном C#-классе, например `Settings` |
| Addressables Prefab | Ресурс, используемый для создания экземпляра |

Переименование Code Name, перестановка записей и замена prefab не меняют ID.
Старые строковые `_id` сохраняются при обновлении каталога; новый GUID создаётся
только для пустого ID. Для копий записей с одинаковым ID инспектор предлагает
явно назначить новые ID повторным записям, сохраняя первую. У копии также нужно
изменить Code Name и выбрать другой prefab.

После добавления/удаления экранов или изменения Code Name повторно генерируйте
**тот же файл**. Старые обращения к переименованным полям выявит компилятор.
Генератор проверяет допустимость C#-имён и дубликаты, экранирует значения ключей и
разрешает перезапись только файла с собственным маркером того же каталога.
Генерация ключей не проверяет готовность content build; ссылки и настройки
загрузки проверяются отдельно при включении root.

Для нескольких каталогов используйте разные имена сгенерированных классов или
namespace. Если код проекта находится в собственной `.asmdef`, добавьте ссылку
на `SimpleUIScreensSystem` для ключей и на `SimpleUIScreensSystem.Addressables`
для использования `AddressableUIRoot`.

Если предпочтителен синтаксис `EScreen.Settings`, задайте Generated Class Name =
`EScreen`: это будет статический класс типизированных ключей, а не enum.

### Кнопки через инспектор

Добавьте `AddressableScreenActions`, назначьте Navigator и выберите Screen из
каталога. В `Button.onClick` назначьте `AddressableScreenActions.Open()` или
`Close()`. Компонент хранит стабильный ID, поэтому переименование Code Name
сохраняет назначение кнопки. Удалённая запись отображается как Missing до выбора
нового экрана. `ScreenId` намеренно не используется как изменяемое сериализованное
поле: для ручной настройки предусмотрен этот компонент.

`ReportAction(string)` по-прежнему можно назначить непосредственно на UnityEvent.
Все вызовы выполняются на главном потоке Unity.

### Миграция предыдущего строкового API

- `EScreenType` удалён. У сценовых `UIScreen` поле `Type` заменено строковым **ID**
  в инспекторе; `UINavigator.Open(EScreenType.X)` → `Open(Screens.X)`, где `Screens` —
  статический класс с `ScreenId` в проекте. `GetScreen` заменён на `TryGetScreen`.
- У существующих записей каталога заполните Code Name (например, `Settings`),
  сохранив прежние ID, затем сгенерируйте класс ключей.
- `Open("settings")` → `Open(Screens.Settings)`.
- `Close("settings")` → `Close(Screens.Settings)`.
- `TryGetScreen("settings", out ...)` → `TryGetScreen(Screens.Settings, out ...)`.
- `ScreenOpened` и `LoadFailed` теперь передают `ScreenId`; строковое представление
  для логов или внешнего хранения доступно через `.Value`.
- Старые UnityEvent-привязки к `Open(string)`/`Close(string)` нужно заменить
  вызовами компонента `AddressableScreenActions`.

Для программно создаваемого каталога или переходного кода можно явно создать
`new ScreenId("existing-stable-id")`. Неявных преобразований и строковых
перегрузок навигатора нет. Ключ должен присутствовать в назначенном каталоге.

## Алгоритм

Предзагрузка сама по себе не повышает популярность. Считаются только успешные
активации по запросу пользователя; повторы `Open` для уже открытого экрана
объединяются и не создают новые наблюдения.

Каждый счётчик затухает:

```text
count(now) = count(last) × 2 ^ (−elapsed / halfLife)

score(screen) = 0.1 × priority
              + ln(1 + recentOpens)
              + 2 × transitionTarget / (transitionTotal + 3)
              + 3 × actionTarget / (actionTotal + 3)
```

- `priority` задаёт начальный порядок, когда статистики ещё нет.
- `recentOpens` отражает частоту открытий с учётом давности.
- Переходы обучаются на последовательности реально открытых экранов. Например,
  после частых переходов «инвентарь → улучшение» окно улучшения получает бонус,
  когда пользователь снова открывает инвентарь. Самопереходы не обучаются.
- `ReportAction` сообщает смысловое действие: выбор раздела, завершение уровня,
  выбор предмета. Самое недавнее действие обучает следующее успешное открытие,
  если оно произошло в пределах окна контекста; затем действие считается
  использованным. При повторении действия его история влияет на рейтинг.
- Добавка `+3` уменьшает влияние контекста, пока наблюдений мало.

Статистика хранится в памяти владельца: сохраняется при отключении/включении того
же root, исчезает при его уничтожении или перезапуске приложения. Сохранения
между игровыми сессиями нет. При отключении корня сбрасывается текущий контекст.
Каталог и настройки нельзя менять во время жизни root; для другого каталога
создайте другой root.

История действий ограничена 32 наиболее недавно использованными именами. Используйте
стабильные ключи вроде `shop.tab_selected`, не подставляйте ID предметов, текст
пользователя или другую постоянно меняющуюся информацию.

## Загрузка и вытеснение

1. Запросы пользователя обслуживаются прежде фоновых запросов. Для разных
   востребованных экранов используется порядок поступления запросов.
2. Повторные запросы одного экрана используют одну Addressables-операцию.
   Если этот экран уже предзагружается, запрос присоединяется к ней.
3. После небольшого периода без действий root периодически пересчитывает
   кандидатов. Каждый фоновой кандидат должен помещаться в бюджет.
4. При отсутствии места можно вытеснить только неиспользуемые загруженные ресурсы,
   уступающие кандидату по рейтингу с учётом заданного запаса.
5. Минимальный срок хранения и запас рейтинга уменьшают частые загрузки/выгрузки
   при небольших колебаниях популярности. При равенстве рейтинга сохраняется
   текущий кеш; начальный выбор определяется порядком записей каталога.
6. Открытые экраны, ожидающие открытия и ещё загружаемые ресурсы учитываются
   в оценке занятой памяти. Открытые экраны защищены от вытеснения. По запросу
   пользователя бюджет может быть временно превышен; свободные ресурсы
   освобождаются, когда это становится возможно.

Предзагрузка вызывает `LoadAssetAsync<GameObject>`: prefab и его зависимости
готовятся в RAM без создания скрытой иерархии. Экземпляр создаётся при открытии,
не более одного за кадр для каждого root. `Instantiate`, `Awake`, построение
Canvas и графические ресурсы всё ещё могут вызвать задержку первого показа.
«Фоновая» здесь означает асинхронную операцию с ограничением конкуренции,
а не выполнение всех этапов на отдельном CPU-потоке.

Закрытые экземпляры уничтожаются, а популярные prefab-ресурсы остаются в кеше.
Состояние формы между открытиями нужно хранить в модели приложения.

## Настройки по умолчанию

| Настройка | Значение | Смысл |
|---|---:|---|
| Max Resident Screens | 4 | Максимум удерживаемых ресурсов, включая загрузки; мягкий для активных запросов |
| Memory Budget MB | 96 | Сумма оценок из каталога; мягкая для активных запросов |
| Max Concurrent Loads | 2 | Максимум одновременно отслеживаемых загрузок |
| Max Background Loads | 1 | Лимит предзагрузок; минимум один общий слот остаётся для пользователя |
| Reevaluate Seconds | 2 | Интервал пересмотра предзагрузки |
| Idle Delay Seconds | 0.5 | Пауза после открытия, закрытия или ReportAction перед предзагрузкой |
| Minimum Residence Seconds | 15 | Защита от вытеснения ради другого фонового кандидата |
| Replacement Score Margin | 0.25 | Минимальный перевес рейтинга для замены |
| Popularity Half Life Seconds | 300 | Через пять минут вес наблюдения уменьшается вдвое |
| Action Context Seconds | 30 | Срок действия контекста последнего действия |
| Failure Retry Seconds | 30 | Пауза перед повторной попыткой неудачной загрузки |

Это исходные настройки, а не универсальный бюджет для устройств. Нулевой бюджет
памяти или количества отключает предзагрузку и хранение неиспользуемых ресурсов.
Явное открытие продолжает работать.

`TrimCache()` освобождает неиспользуемые ресурсы и временно приостанавливает
предзагрузку. Уже начатые загрузки продолжают занимать слоты до завершения, после
чего освобождаются, если пользователь их не запросил. Событие
`Application.lowMemory` вызывает ту же процедуру. Экземпляры, уничтожаемые в этом
кадре, удерживают prefab до следующего кадра.

## Контракт жизненного цикла

- `Open` ставит запрос. `ScreenOpened` сообщает об активации; анимация к этому
  моменту может ещё продолжаться. Подписывайтесь до `Open` и симметрично отписывайтесь.
- `LoadFailed(id, exception)` сообщает об ошибке, включая вызовы во время cooldown.
  Без подписчика root выводит предупреждение. Ошибки пользовательских обработчиков
  логируются отдельно и не останавливают очередь.
- `Close` отменяет ожидающее открытие, чтобы завершившаяся позже загрузка не
  открыла уже ненужное окно. I/O Addressables при этом не отменяется.
- Повторное открытие во время закрытия ждёт уничтожения закрывающегося экземпляра.
- Prefab создаётся под неактивным техническим контейнером. `Init()` выполняется
  **до `Awake()`**, затем экран активируется. Производные экраны должны получать
  необходимые для `Init()` ссылки в самом `Init()` или из сериализованных полей.
- При отключении root подписки удаляются, экземпляры уничтожаются, освобождение
  handles передаётся независимому получателю обновлений ResourceManager. Остановка
  игровых корутин не отменяет очистку.
- Событие `UIScreen.OnClosed` следует активности объекта: внешнее выключение
  экземпляра или его родителя также означает закрытие. Внешний контейнер должен
  быть активен при открытии.
- Не вызывайте `Destroy` для prefab-ресурса и не освобождайте handles из внешнего
  кода. Загрузчик владеет ресурсами, экземплярами и их очисткой.

## Проверка памяти и упаковки

Оценка MB не является измерением RAM. `GetDownloadSizeAsync` описывает скачивание,
а не резидентные текстуры, шрифты и экземпляры. Размеры каталога нужно подбирать
по профилированию типичных экранов на целевых устройствах; общие зависимости
могут привести к завышенной сумме оценок.

Addressables использует подсчёт ссылок. Освобождение одного экрана не обязательно
освобождает его память немедленно: другие экраны могут удерживать тот же bundle.
Разделяйте редко используемые тяжёлые экраны по содержимому и отдельно анализируйте
общие атласы/шрифты; проверяйте дублирование зависимостей. Не вызывайте
`Resources.UnloadUnusedAssets` при каждом закрытии.

Документация Unity: [Managing Addressable asset memory](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/memory-assets.html).

Для диагностики доступны `ResidentScreenCount`, `EstimatedResidentMemoryMB`,
`TryGetScreen`, события открытия и ошибок. Лимиты действуют на один root;
несколько root имеют независимые кеши и отдельные лимиты.

## Тесты

`Tests/Editor` проверяет ключи, затухание, приоритеты, обучение переходам, контекст
действий и ограничение истории. `Tests/Editor/Generation` проверяет генерацию C#,
дубликаты, допустимость имён, экранирование и принадлежность файла каталогу.
`Tests/PlayMode` использует настоящий
Addressables ResourceManager с управляемым провайдером в памяти: проверяет
совместное использование операций, отмену открытия, конкуренцию, удержание
ресурсов и очистку. Тестовый провайдер не моделирует задержки диска, сети,
упаковку bundles или GPU; для этих измерений нужен content build и player.
